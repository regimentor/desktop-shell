# Какой механизм переключения выхода поддерживает лаунчер

## Question

Какую предпосылку окружения принимает спецификация для переключения выхода приложения: WirePlumber с переносом через metadata или pipewire-pulse с подтверждённым покрытием нужных потоков?

Исследование установило, что одного документированного QML API Quickshell недостаточно для переноса. До выбора проверить доступное окружение и сопоставление идентификаторов без изменения аудиосессии; факты выясняет агент, допустимые зависимости согласует пользователь. Зафиксировать основной путь, необходимость запасного варианта и поведение при отсутствии выбранного механизма.

Также определить, как интерфейс подтверждает результат и показывает отказ переноса либо исчезновение выбранного устройства. Не обещать успешное переключение только на основании отправки команды.

## Comments

Выявлено при разрешении [Возможностей интеграции PipeWire с Quickshell](01-pipewire-integration.md). Рекомендация исследователя не является утверждённым выбором.

Проверка окружения агентом audio_environment: установлены PipeWire 1.6.8, WirePlumber 0.5.17 и pactl 17.0-98-gb096. Проверка `systemctl --user is-active` вне ограничения sandbox подтвердила active для pipewire, pipewire-pulse и wireplumber. Аудиосессия не изменялась; успешность реального переноса не проверялась.

Повторно проверена [официальная политика WirePlumber](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html): обновление target.object metadata поддерживает перенос, если политика конкретного потока его не запрещает.

Предложение на согласование:

- Quickshell наблюдает состояние, управляет громкостью и mute; небольшой адаптер через pw-metadata запрашивает перенос каждого потока приложения средствами WirePlumber. Запасной адаптер pipewire-pulse в первую версию не включать.
- При недоступности механизма переноса выбор выхода недоступен с понятной причиной; остальные доступные звуковые контролы продолжают работать.
- При выборе выхода интерфейс показывает ожидание и подтверждает результат по фактическим связям потоков. Отказ или частичный перенос явно отображаются; отправка команды не считается успехом для всего приложения.
- При отключении выбранного устройства требуется решение пользователя: переходить на системный выход по умолчанию или оставлять приложение без звука до выбора доступного выхода.

Дополнительная read-only проверка audio_environment: `/usr/bin/pw-metadata` доступен, `wpctl settings linking.allow-moving-streams` показывает `Value: true`. Реальные переносы и ограничения конкретных потоков не проверялись.

Пользователь ответил «1да 2да»: принят предложенный механизм и рекомендация оставлять приложение без звука при отключении выбранного устройства.

## Answer

- Использовать Quickshell для наблюдения состояния, громкости и mute; переносить потоки приложения через адаптер `pw-metadata` и WirePlumber (`target.object`). Не включать запасной адаптер через pipewire-pulse в первую версию.
- Предпосылки окружения подтверждены: WirePlumber работает, pw-metadata доступен, глобальная политика разрешает перенос. Успешность переноса конкретного потока определяется по фактическому состоянию.
- При выборе выхода показывать ожидание; завершать переключение только после подтверждения связей потоков. Ошибки и частичный перенос отображать явно.
- Если механизм переноса недоступен, отключать выбор выхода с понятной причиной, сохраняя остальные доступные контролы.
- Поведение при отключении устройства пересмотрено в [Как лаунчер реагирует на потерю выхода](08-disconnected-output.md); прежний запрет автоматического перехода отменён.

Выбран механизм явного переключения выхода; поведение при изменении доступности устройств определяется связанным решением выше. Реальные переносы на этом этапе планирования не проверялись.
