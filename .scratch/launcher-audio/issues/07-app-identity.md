## Question

Как лаунчер получает восстановленные настройки приложения и группирует его текущие потоки? Исходная задача собственного восстановления и определения полного закрытия пересмотрена пользователем в пользу штатного состояния PipeWire/WirePlumber.

## Comments

Начато исследование доступных признаков приложения и его жизненного цикла агентом app_identity_facts. Пользователю отправлены независимые вопросы: объединять ли несколько окон/профилей под одной строкой и сохранять ли громкость/выход между перезапусками оболочки и компьютера. Рекомендация агента по обоим — да; ответы ещё ожидаются.

### Результат проверки фактов

- `application.id` — логическая идентичность приложения. PID и runtime-идентификаторы узла/клиента не подходят для хранения между запусками. [Ключи PipeWire](https://docs.pipewire.org/group__pw__keys.html).
- В локальном AppModel.qml каталог использует DesktopEntries; процесс запуска через uwsm не является наблюдателем всей жизни приложения. Точное `byId` и потенциально ошибочное `heuristicLookup` различаются; эвристика пригодна для оформления, но не доказывает идентичность для объединения настроек. [DesktopEntries](https://quickshell.org/docs/v0.3.1/types/Quickshell/DesktopEntries/).
- Вывод из [API потоков](https://pipewire.pages.freedesktop.org/pipewire/group__pw__stream.html): поток может быть уничтожен/отключён отдельно от приложения. Поэтому пропажа последнего потока не является подтверждением полного закрытия приложения.
- WirePlumber штатно восстанавливает громкость и mute потоков. Локальный state-stream.lua использует цепочку application.id → application.name → media.name → node.name с учётом media class; это ключ состояния потока, не универсальная идентичность приложения. [Настройки WirePlumber](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html).

Предлагаемый технический подход: точный логический app ID для устойчивой группировки; при недостатке метаданных не объединять произвольные приложения по совпадению отображаемого названия. Не использовать PID или заголовок вкладки как долговременный ключ. Конкретный fallback и владелец восстановления зависят от выбранной пользовательской политики.

Дополнительное предложение пользователю: сохранить штатное восстановление mute WirePlumber, пересмотрев прежний сброс после полного закрытия. Это устраняет необходимость угадывать закрытие приложения по потоку. Предложение ещё не принято; прежнее решение не изменено.

Пользователь предложил при запуске брать состояние через WirePlumber и подтвердил объяснение: актуальные значения читаются через Quickshell/PipeWire, восстановление принадлежит WirePlumber, отдельное хранилище лаунчера и автоматический сброс mute исключаются.

## Answer

- Источник истины — текущее состояние PipeWire. При запуске лаунчер подписывается на узлы через Quickshell и показывает фактические громкость, mute и связи с устройствами после готовности соответствующих объектов. Восстановление WirePlumber может приходить последующими событиями; единовременный снимок не заменяет подписку.
- Громкость, mute и выбранный выход восстанавливаются штатными средствами WirePlumber согласно его доступным метаданным и политике. Лаунчер не создаёт собственного долговременного хранилища этих настроек и не гарантирует восстановление поверх ограничений WirePlumber.
- После запуска, появления потока или смены устройства лаунчер не перезаписывает состояние своими старыми значениями. Пользовательские действия применяются к текущим узлам; затем интерфейс отражает подтверждённое состояние.
- Прежний автоматический сброс mute после полного закрытия приложения отменён. Не требуется определять закрытие приложения по исчезновению потока или отслеживать его процессы ради сброса.
- Для текущего представления приложения основной ключ — точный `application.id`. При его отсутствии технический fallback ограничен явно связанными потоками одного клиента в текущем соединении; при отсутствии и этого признака поток остаётся отдельной неизвестной группой. Одинаковое отображаемое название не является достаточным основанием объединения. Runtime-ключи не сохраняются между запусками.
- DesktopEntries используется для названия и иконки; эвристический поиск не определяет принадлежность сохранённых настроек. Окна/профили с одинаковой логической идентичностью неразличимы для этого представления; отдельные потоки остаются доступны.

Приложения без существующих потоков не добавляются в результаты только на основании сохранённого состояния. Общие действия по приложению и отдельные действия по потоку сохраняются согласно связанному решению.
